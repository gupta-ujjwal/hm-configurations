Engineering Intelligence in a Payments SDLC
A working brief from our engineering team

Controlled engineering acceleration.

How we use AI to ship faster across the SDLC of a payments platform — and the controls that keep it safe to do so.

Euler Engineering · Internal Reference Deck
The context

In payments, "faster" has to mean safer too.

A change to an acquiring platform travels through many stages before it reaches production. Setting up an environment. Designing the change. Implementing it. Reviewing it. Each stage has its own drag — and every stage carries risk.

The temptation with AI is to optimise one stage (code generation) and call it productivity. We took the harder path: map the full lifecycle, find friction at each stage, and build acceleration into each — with controls scoped to the risk that stage introduces.

The rest of this deck is how that breaks down — four pillars across the SDLC, the controls model that sits underneath them, and an end-to-end example.

PILLAR I Setup Reproducibility as a control surface.

A new machine becomes a working dev environment in one command.

Every engineer's tooling — agents, skills, MCPs, services, databases with seed data, dotfiles — is declared in a version-controlled configuration. Provisioning is deterministic. There is no "works on my machine" surface where shadow tooling can hide.

What it enables

Zero-to-hacking, repeatably

  • Onboarding a new engineer takes minutes, not days
  • Same dev environment on laptop, VM, or CI runner — by definition
  • Every tool, model, and workflow is configuration, not folklore
  • Agents inherit the same environment as humans — no privileged setup
Controls in place

What this contains

  • No undocumented developer tooling can enter the SDLC
  • Configuration changes are auditable — same review process as code
  • Models and agents available to engineers are an explicit, reviewed list
  • Eliminates "key person" risk in environment knowledge
PILLAR I Setup · Orchestration Many sessions, one auditable workbench.

Parallel work, single point of observation.

An engineer working on a change to an acquiring flow may have multiple AI sessions running concurrently — researching, drafting, testing. We unified these behind a single web client so that what each session is doing remains observable and recoverable.

PILLAR II Design Frame, pressure-test, and plan before any code is written.

Our engineering principles are encoded, not assumed.

For a change to a payments platform, "works" is a low bar. Every approach proposed during design is pressure-tested against two internal frameworks before it reaches an engineer for sign-off — the same frameworks our senior engineers apply by hand.

Encoded in the design workflow

Two internal frameworks, applied to every proposal

Four Shapes — every idea is examined through four lenses: shape of the domain, the product, the nature of the change, and the theory behind the approach.

10 Reliability Tenets — non-negotiable properties for production code in a payments environment. Every approach runs the full list; tenets at risk are surfaced explicitly.

Controls in place

What this contains

  • No design moves to implementation without an approved plan
  • Pressure-testing is uniform across engineers — not dependent on individual rigour
  • The plan, alternatives, and rejected approaches are all recorded
  • Knowledge of our standards is captured in the workflow, not in heads
PILLAR III Implement Build the change, validate against real production behaviour.

ART — production safety, replayed in local.

ART records real transactions in production — incoming and outgoing API calls, database operations, every side effect — and replays them against any new build in a local environment. The premise: if everything that worked in production yesterday still works against today's code, the change has not broken anything that matters.

What this enables

Regression risk caught before PR

  • Behavioural drift is detected on the engineer's machine, not in QA
  • The "blast radius" of any change is observable before it leaves local
  • Works equally for human-written and AI-written changes — no carve-out
  • Foundation for the autonomous loop, covered later in this deck
Controls in place

What this contains

  • Implementation runs in local sandboxes — no AI process touches production
  • ART evidence is attached to every PR, visible to reviewers
  • Failures surface the divergent transaction with full replay context
  • Production recording is privacy-aware — sensitive data masked at capture
PILLAR IV Review Humans review intent. Agents review mechanics.

A two-pass review, with the human pass mandatory.

For any change touching production paths, human sign-off is required and gate-enforced. The agent pass exists to make the human pass higher-leverage, not to replace it.

Pass 01 · Agent

Mechanical pass

Runs the change through the reliability tenets, complexity analysis, intent-vs-implementation comparison, and surface-level issue detection. Catches the things humans are bad at being consistent about, before the human's time is spent.

Pass 02 · Human · Mandatory

Intent pass

A reviewer-friendly view surfaces what changed in the system — which flows moved, which contracts shifted — rather than a raw diff. The human evaluates the shape of the change against business intent. No production-touching change merges without this pass.

The controls model

Acceleration and containment, by design.

The four pillars accelerate the SDLC. The controls underneath them define what stays bounded — what AI can do, what it cannot, and what evidence exists that the boundary holds.

Data residency
Self-hosted models for prod-data workflows
Any workflow that may touch production data — logs, configs, traffic captures — runs against models hosted on our own GPUs. Nothing leaves our infrastructure.
Approval gate
Formal sign-off for prod-touching change
No AI-generated change reaches a production-affecting path without explicit human approval, enforced at the review gate. Class of change determines the gate.
Auditability
Full action log, per agent, per change
Every AI action is logged with attribution: which agent, on whose authority, against which artefacts. Reconstructable on demand.
Environment isolation
No direct production access
AI processes run in local sandboxes. Read access to production telemetry is mediated and logged. Mutation paths to production require a human-initiated deployment.
Secret hygiene
Credentials never enter agent context
Secrets are referenced, not embedded. Agents work against masked surrogates; live credentials remain in the deployment layer.
Policy-aware workflows
Compliance encoded in the pipeline
Workflow templates carry compliance constraints (PCI, regional residency) so engineers don't carry them in working memory. Violations are surfaced at design time.
Human-in-the-loop boundaries

A clear line between what AI does and what humans must.

Ambiguity here is where AI projects in regulated environments fail. We are deliberate about which actions are AI-delegated and which require a human in the loop.

What AI does
  • Research the codebase and produce design proposals
  • Pressure-test approaches against our reliability tenets
  • Generate and implement code changes per an approved plan
  • Run local validation, ART replay, and self-review
  • Surface PRs with structured context for human review
  • Answer factual product questions across roles
What humans must do
  • Approve any design plan before implementation begins
  • Sign off on any change that touches a production path
  • Make the deployment decision and initiate the deploy
  • Adjudicate compliance edge cases flagged by the workflow
  • Authorise any change in scope for an agent's role
  • Hold accountability for the change — full stop
Two classes of workflow

We distinguish production-safe from experimental.

Conflating these is the most common mistake we see when AI is introduced to regulated SDLCs. We treat them as fundamentally different operating modes, with different controls.

Production-safe · default

The four-pillar lifecycle, controls on

Any change touching production paths runs through Design → Implement → Review with full controls: approval gate, mandatory human sign-off, ART validation, full audit trail. This is the only mode that ships to merchants.

HUMAN SIGN-OFF: required
ART VALIDATION: required
AUDIT: complete
APPLIES TO: any prod-affecting change
Experimental · bounded

Autonomous loop, ART-gated

For a narrow, well-defined class of non-behavioural change — refactors, runtime upgrades, perf optimisations — ART provides enough signal to run the loop without per-change human review. ART failure is the gate.

ELIGIBILITY: non-behavioural changes only
ART VALIDATION: required, blocking
HUMAN: scopes the work, reviews outcomes
CURRENT USE: runtime upgrades, perf

The autonomous loop is a deliberate, scoped operating mode — not a general posture. A change qualifies for it only if it carries no behavioural or functional intent. Everything else runs through the production-safe lifecycle.

Inside the experimental mode

The loop, in detail.

Plan → Implement → Build → Run ART. On pass, the agent picks up the next chunk. On fail, ART surfaces the diverging transaction for a human. The loop is bounded by ART coverage and by the change classification gate from the previous slide.

Pass — agent picks up the next chunk, loop continues. Fail — ART surfaces the divergent transaction; human takes over.
Running today

Runtime version migration

A multi-week upgrade touching large parts of the codebase. Pure regression scope, no behavioural drift — the change class the loop is built for.

Next

Performance optimisations

Same shape — measurable, no behavioural drift — same loop. We expect scope to expand only as ART coverage justifies it.

Knowledge continuity

Engineering capability that doesn't depend on individuals.

A common concern with sophisticated engineering organisations is concentration of knowledge in a small number of people. AI, used carelessly, makes this worse. Used the way we use it, it does the opposite.

Encoded, not tribal

Standards live in workflows

Our reliability tenets, design philosophies, and review checks live inside the agent workflows. They apply to every change, every engineer, every time — not only when a senior engineer happens to be in the room.

Onboardable, not arcane

The system can be handed over

A new engineer joining the team picks up the same workflows on day one. The institutional knowledge of how to make a safe change to this platform is in version control, not in a senior's head.

Auditable, not opaque

Every change leaves a trail

The full reasoning — design alternatives considered, tenets at risk, replay evidence — is captured per change. Post-incident review, regulatory audit, or handover all draw from the same source.

Available, not exclusive

Research, on demand, across roles

Product questions, debugging context, configuration history — answered against the live system by a self-hosted research agent. Available to engineers, PMs, and BD on the same footing.

On the roadmap

Where this goes next.

Each item extends the same model — more of the SDLC accelerated, the same controls applied. Scope expands only where the controls keep pace.

Extends · cross-pillar collaboration

Agents inside our workplace

Wiring these agents into our internal workplace platform with role-aware auth and scoped data access. The shift: from individuals prompting an agent in isolation, to PMs, engineers, and BD genuinely collaborating with agents in the threads where the team already works.

Extends · documentation as control

Self-healing documentation

Scheduled workflow that reviews documentation against the current state of the codebase and updates it. Documentation drift compounds silently — closing the loop turns docs into a continuously-attested artefact.

Extends · strategic insight

Product-market-fit reporting

Periodic workflow that reads our codebase, scans the market and competitors, and produces a structured PMF report with action items. Turns ambient market signal into something the team can act on.

Extends · compliance posture

Continuous compliance sweep

Workflow that ingests relevant regulatory frameworks across the geographies we operate in, evaluates the platform against them, and surfaces inconsistencies or upcoming changes we need to plan for. Compliance becomes a monitored property, not a periodic project.

In closing

A controlled engineering acceleration system, not a copilot.

Most AI-in-engineering stories optimise a single step. We treated the SDLC as four pillars and built acceleration into each one — with self-hosted models for sensitive workflows, mandatory human sign-off where it matters, and a complete audit trail underneath.

The result isn't "faster coding." It's engineering capability that ships faster, depends less on individuals, leaves a clearer trail, and remains containable as scope expands. That's the shape of the system.
